# 为什么 DSH 需要一份「兼容性基线」

DSH 的插件生态正在以远超任何人跟踪能力的速度膨胀。官方口径是约 3.5 万个第三方插件，GitHub 上带 `dsh-plugin` topic 的仓库已超过 3 万。与此同时，DSH 仍是 developer preview：30 天发了 10 个预发布，README 明确写着会有破坏性变更。

于是一个很实际的问题出现了：**当一个插件说「支持 DSH」时，它到底支持哪个版本？**

大多数插件没有回答。我们抓了 44 个插件（20 个已知的头部插件 + 24 个从 npm 搜索补进来的外部插件），只有 24 个在 `package.json` 里声明了 `engines.dsh`；剩下 20 个是 unknown。也就是说，接近一半的插件，**在安装之前你无法从元数据判断它是否覆盖你正在用的 DSH 版本**。

这就是 HCB（Host Compatibility Baseline）想解决的问题。

## HCB 做了什么

HCB v0.1 很小，只做三件事：

1. **把 host 版本固定下来**：从 DSH 的 GitHub Releases 取 39 个 release，取最近 10 个进入矩阵。
2. **把插件的声明读出来**：从 npm registry 读 `engines.dsh`、`peerDependencies`、`dsh.capabilities`、`dsh.manifestVersion`。
3. **算出一个三态矩阵**：`declared-compatible`、`declared-incompatible`、`unknown`；并聚合 capability 面（谁能读文件、谁能联网、谁能起子进程）。

它不是测试结果。**声明兼容 ≠ 实际可用**。一个插件可以声明 `>=0.2.0 <0.3.0`，但在 `0.2.2-rc.3` 上仍然崩——这需要 v0.2 的 tested matrix。但“声明”是第一步：如果连声明都没有，测试就无从谈起。

## 首版看到的三个事实

- **44 个插件里，24 个有声明，20 个 unknown**。外部插件比头部插件更容易缺声明。
- **声明范围普遍滞后**：不少插件还停在 `>=0.1.x`，而 host 已经到 `0.2.2-rc.3`。
- **capability 面高度集中**：`tools:register`、`network:egress`、`subprocess` 是前三名；这意味着“装一个插件”经常等于“给 agent 加一组工具 + 网络 + 子进程能力”。

## 怎么用

- **升级前**：查一下你要升到的 host 版本，是否还在插件的声明范围内；不在，就先别升，或者准备迁移。
- **安装前**：看 capability 面。一个只读插件不应该要求 `subprocess`。
- **CI 里**：把 `declared-incompatible` 当 warning，把 `unknown` 当 info；不要一上来就 fail，否则生态会被吓跑。
- **写插件时**：加一行 `engines.dsh`。这是成本最低、收益最高的兼容性投资。

## 它不是什么

- 不是安全审计。声明了 capability 不等于实际只做这些事。
- 不是排行榜。`declared-compatible` 是作者自述，不是质量背书。
- 不是官方项目。它是社区维护的独立基线，不代表 DeepSeek 立场。

## 下一步

v0.2 会做 top 20 插件 × 5 个 host 的 **tested** 矩阵，每个格子附 Docker 复现脚本；v0.3 会做版本间的 capability diff 和 stale 提醒。

如果你维护插件，欢迎把包名加进 `data/plugins.seed.json`，或者直接提 PR 补 `engines.dsh`。如果你在企业里用 DSH，欢迎告诉我们你最关心哪几个插件——我们会优先测。
